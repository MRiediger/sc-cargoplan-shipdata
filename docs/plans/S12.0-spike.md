# S12.0 Spike – Plan

Approved by Claude.ai on 17 Nov 2026 with K1 (gate-b renders both states in one job) and E1–E3, incorporated below.

## Context

v0.5.1 took half a day of manual work for three new ships. Phase 12 therefore builds a pipeline in
`sc-cargoplan-shipdata` that runs without Martin. Before the pipeline is built (T12.1/T12.2), this spike takes **one
ship** through GitHub Actions to measure the five questions whose answers change the design. Spike code is thrown away.
It only measures.

## What exploration already settled (shapes the spike)

- **Script names:**
  - `fetch.ps1`, `trace.py`, `bundle.py` and `sheet.py` are the old Fleetyards chain in `legacy/`.
  - Today's Motherlode chain is `fetch-motherlode.ps1` → `holo_mesh.py flatten-model → cull` → `simplify.mjs` (ladder
    20k/30k/40k) → `holo_mesh.py export → outline → outlines-v2`.
  - The **anchor** is not computed in `sc-ship-outlines` but in `sc-cargoplan/tools/import-motherlode.ps1`.
- **No GPU and no display anywhere in the chain.**
  - It needs only numpy, opencv-python-headless, Node with meshoptimizer (WASM) and PowerShell. There is no Blender.
  - Windows assumptions live in `decimate.ps1` and `run-all.ps1` (`.venv\Scripts\python.exe`, backslash paths).
  - `tests/test_fetch.py` spawns `powershell`, which does not exist on Linux.
- **Only the catalog needs the API secret.** Model URLs are not in the API response:
  - They are scraped from the page `cryon.rocks/ops/cargo` (RSC stream, no key).
  - The models themselves sit in a public Supabase bucket
    (`…supabase.co/storage/v1/object/public/ship-models/<Class>-<hash12>.glb`).
- **Secrets scan of `sc-ship-outlines`:**
  - No hardcoded keys.
  - `motherlode/api-key.txt` exists only locally, is gitignored and was never committed.
  - I scan the copied files again before porting.
- **`ShipPictureTests` compares SHA-256 hashes of the raw BGRA pixels: exact, with no tolerance**
  (`ShipPictureTests.cs:187-189`).
  - The baseline is an earlier run's OUT folder (`pictures.csv`, `values.csv`), not a folder of images.
  - Environment variables control it: `CARGOPLAN_PICTURES_OUT`, `CARGOPLAN_HOLO_FOLDER`, `CARGOPLAN_PICTURES_BASELINE`
    and `CARGOPLAN_PICTURES_EXPECTED`.
  - `ships/` and `outlines/` are read from the `bin` folder, with no override. CI must therefore replace the files in the
    checkout before the build.
  - CI has never run this test (`Category=Slow`). Other WPF tests already run there with software rendering (D98).
  - `ViewPictures.Difference()` (share of differing pixels) exists, but the test does not call it.
- **`holo-v3` is a pre-release in `MRiediger/sc-cargoplan`.** The repo is public and the release has 103 assets, so the
  cross-repo checkout and the release download need no extra token.
- **`TOOLS.md` is not in the app repo. It is in `sc-ship-outlines`.** The pins are:

  | Tool | Pin |
  |---|---|
  | Python | 3.14.5 |
  | numpy | 2.5.3 |
  | opencv-python-headless | 5.0.0.93 |
  | Node | 24.16.0 |
  | meshoptimizer | 1.3.0 |
  | .NET SDK (from the app repo's `global.json`) | 10.0.404 |

## Ship: ORIG 100i (`100i` / `orig-100i` / `ORIG_100i`)

- **Grid:** one internal grid `[1,2,1]`, 2 SCU, translation only, no rotation, one rack.
- **Holo in `holo-v3`:** `orig-100i.holo`, 93,794 B.
  - It is byte-identical to holo-v2 and to the local `holo-work-ml/ORIG_100i/PP.holo`, so it was stable across two runs.
- **Model size:** 8,057 triangles, below the 20k budget.
  - The ladder runs but simplifies nothing (`errorM` 0).
  - So the spike measures platform drift of flatten, export and outline, without noise from simplification.
- **Fallback if the 100i model hash changed in the fresh catalog:** Avenger Titan, then Nomad.
  - Both are just as simple; Nomad tests `judge` harder.
  - The pick comes from the same catalog, with no second API call.
  - The workflow input `ship` defaults to `ORIG_100i`.

## Workflow `.github/workflows/spike.yml` (`workflow_dispatch` only)

Every step ends with three lines in the log and in `$GITHUB_STEP_SUMMARY`: **checked / found / to do**. The numbers also
go to `spike/out/<job>.json`. A small helper, `spike/say.sh`, writes both.

### Job `chain` (ubuntu-latest): questions 1 and 2

1. **Setup.**
   - Check out this repo, plus `MRiediger/sc-cargoplan@v0.5.1` into `app/`.
   - `setup-python` 3.14.5, `setup-node` 24.16.0, `npm ci`, `pip install -r`.
   - Log the setup time and the version actually installed for each tool.
2. **Catalog, exactly once.**
   - `actions/cache` with key `spike-catalog-v1`. Caches are repo-internal, not public.
   - Only on a cache miss does `pwsh fetch-motherlode.ps1 -SkipModels` run with `MOTHERLODE_API_KEY`, so re-runs never
     call the API again.
   - Logged: HTTP status of the API and the page, rate-limit and Cloudflare headers, duration, size, `gameBuild`, catalog
     SHA-256.
   - Catalog and models **never** go into public artifacts (licence).
3. **Scraper probe (question 2).**
   - `HEAD` all ~105 model URLs from the catalog, 200 ms apart, no retry.
   - Measure:
     - status distribution
     - latency p50/max
     - sum of `Content-Length` (the cold cache size)
     - rate-limit headers
   - `GET` only the spike ship's model and check its SHA-256 against the model name in holo-v3.
   - **(E2) No GET besides that one model.** The step summary counts every outbound request, e.g.
     "1 API call, 1 page GET, 105 HEAD, 1 model GET" (0 API and 0 page calls on a cache hit). Sciirof has not yet
     answered the monthly-run request, so the spike also shows how quiet the pipeline can be.
   - **If the page is blocked (Cloudflare):** fall back to the known 100i URL from the 16 Nov catalog. The block becomes a
     finding and the chain continues.
4. **Chain (question 1).**
   - `flatten-model → cull → simplify ref → ladder (simplify + export, stop at the first pass) → outline → outlines-v2`.
     The only entry in `outlines-v2` is 100i, with v0.5.1's outlines as the previous file, so every other ship stays.
   - Then `pwsh import-motherlode.ps1 -Catalog … -ShipsFolder <copy> -Outlines <new> -ModelMap …` for the anchor.
   - Measure seconds and output size per step, and the work folder size per ship, extrapolated to 101 ships.
5. **Comparisons (bytes, platform drift).**
   - **Built `orig-100i.holo` vs the holo-v3 asset (SHA-256).** If they differ: header counts and the maximum vertex
     deviation.
   - **Outline entry vs v0.5.1:** equal, or the maximum point deviation in mm, plus `floorM`.
   - **`ships/100i.json` vs the v0.5.1 git blob:**
     - Compare LF-normalized, because of `* text=auto`.
     - If they differ, put a unified diff in the log.
     - Suspect: the timestamp in `source`, because pwsh 7's `ConvertFrom-Json` converts dates.
   - **`PP.json` metrics vs the manifest entry.**
   - **Side number:** how many of the 108 ship files the import rewrites with the fresh catalog.
6. **Artifact `built`** (kept 7 days): `orig-100i.holo`, `ship-outlines.json`, `100i.json`, `PP.json` and the numbers
   JSON. All of it is derived data that is already public in holo-v3.

### Job `gate-a` (windows-latest, parallel to `chain`): question 3 and half of question 4

1. **Setup.**
   - Check out `sc-cargoplan@v0.5.1` into `app/`; `setup-dotnet` via `global.json`.
   - Download the `holo-v3` and `holo-v2` assets with `gh release download` and `GITHUB_TOKEN`.
   - `dotnet build -c Release`.
2. **Run A1.**
   - Command: `dotnet test tests/CargoPlan.App.Tests -c Release --no-build -p:RunSettingsFilePath= --filter FullyQualifiedName~ShipPictureTests`
   - OUT=`a1`, HOLO=holo-v3, no baseline, so every PNG is written.
   - Logged: does WPF render, picture count, duration, the runner's `ImageVersion`, and the `segoeui.ttf` file version.
3. **Run A2.**
   - Same as A1 with HOLO=holo-v2 and BASELINE=`a1`.
   - It fails as expected (`continue-on-error`).
   - It gives the image pairs of **real changes** (the 20 ships changed v2→v3) for question 4.
4. **Artifacts:** `a1` (CSV + PNGs) and `a2` (CSV + only the differing PNGs). Measure the artifact sizes.

### Job `gate-b` (windows-latest, `needs: [chain, gate-a]`): question 3 as the target gate

This job holds the measurement that decides the production gate: **same VM, old state against new state**. In the
pipeline, baseline and candidate both come from the Ubuntu run and are rendered on the same Windows runner. Runner drift
and Ubuntu/Windows drift of holo generation then drop out by construction, and only real changes remain.

1. Check out `sc-cargoplan@v0.5.1`, build, and fetch the holo-v3 assets.
2. **Run B0 (K1):** unchanged `v0.5.1` with holo-v3, OUT=`b0`, no baseline.
3. Swap in the files from `built`:
   - `ships/100i.json`
   - `outlines/ship-outlines.json`
   - `orig-100i.holo` inside the holo-v3 folder

   Then rebuild, because `ships/` and `outlines/` are copied into `bin`.
4. **Run B:** ShipPictureTests with BASELINE=`b0` and EXPECTED=`100i`. This is the target gate job: cross-repo checkout,
   both states rendered, and the test run, all in one job.
5. **Also compare B against `a1`** (artifact from gate-a), so the VM↔VM number stays.
6. **Results:**
   - **B0↔B:** are all non-100i pictures hash-equal? If yes, the production gate is "render both states in the same job,
     hash-exact, only changed ships may differ". It needs **no stored baseline and no tolerance mode**. The threshold
     from question 4 is then needed only for the judge (how much did a changed ship change?), not for the gate.
   - **B↔a1** (non-100i): do two runner VMs render bit-identically?
   - **100i in B0↔B:** equal or different? That shows whether the Ubuntu chain gives the same pictures as Windows.
   - **Duration of the swap and the rebuild** (input for E3).
7. **Artifacts:** `b0` (CSV only) and `b` (CSV + differing PNGs).

### Local (I run it; Martin types nothing): question 4

1. **Reference run on Martin's machine.**
   - `git clone --branch v0.5.1 ..\sc-cargoplan` into the scratchpad.
   - holo-v3 comes from the local `sc-ship-outlines\holo\ml\release-v3`, its SHA-256 checked against the manifest first.
   - Same test command as A1, OUT=`local`.
2. **Fetch the artifacts** with `gh run download` (`C:\Program Files\GitHub CLI\gh.exe`).
3. **`spike/compare.py`** (numpy + cv2, run with the `sc-ship-outlines` venv and `-I`) computes three measures per
   image pair:
   - share of differing pixels, exactly as `ViewPictures.Difference`
   - share of pixels with a channel delta above 8
   - SSIM: grayscale, Gaussian 11×11, σ 1.5 (Wang 2004)
4. **Four pair classes:**
   - **same / same VM:** `b0` ↔ `b` without 100i (expected identical; the hash count from gate-b is enough)
   - **same / different machine:** `local` ↔ `a1`
   - **same / different VM:** `a1` ↔ `b` without 100i
   - **different:** `a1` ↔ `a2` (holo-v2 vs v3)
5. **Output.**
   - Per measure: max and p99 of the "same" classes, min and p1 of the "different" class.
   - The threshold goes in the gap, with a margin. If there is no gap, that is itself a finding.
   - Also count how many hashes match between `local` and `a1`. That decides whether a locally made baseline can work at
     all.

## Expected risks (what the spike measures instead of solving)

| # | Risk | What the spike does |
|---|---|---|
| R1 | `cryon.rocks/ops/cargo` blocks datacenter IPs (Cloudflare) | Log status and headers, use the 100i URL fallback. Finding: model URLs need another route. |
| R2 | API 429 or a key problem | Exactly one call; the cache prevents repeats. A finding, not a retry. |
| R3 | Python 3.14.5 is missing in `setup-python`, or wheels are missing (opencv 5.0.0.93 cp314 manylinux) | Log the version actually installed; a deviation from the pin is a finding. |
| R4 | pwsh 7 on Linux: `ConvertFrom-Json` converts dates, backslash default paths (`outlines\ship-outlines.json`), CRLF/LF | Pass `-Outlines` and `-ShipsFolder` explicitly. The `100i.json` diff shows where. |
| R5 | numpy/cv2 floating point on Linux ≠ Windows, so holo and outline are not byte-equal | Measure the maximum deviation; image comparison in gate-b. |
| R6 | The hash-exact picture test: Martin's baseline ≠ the runner's; a runner image update changes fonts | Count hash matches local↔a1 and a1↔b; threshold from question 4. |
| R7 | ~1,400 PNGs make the artifact too large or too slow | Measure size and upload time. |
| R8 | WPF rendering on windows-latest in a service context | A1 shows it. Other app tests already run there (D98). |

## Exit plan for the external source

The catalog lives in the cache and the derived data in the artifact. If Motherlode drops out, the spike continues with
the cached catalog and the 100i fallback. For the pipeline this means the last data release stays valid.

## Numbers that end up in `TASKS.md` ("S12.0 Befund")

1. **Chain:**
   - runs yes/no
   - seconds per step and per job
   - setup time per tool
   - installed versions vs the pins
   - cache sizes: catalog bytes, model bytes for one ship and for all of them (sum of `Content-Length`), work folder per
     ship ×101
   - holo, outline and ship JSON byte-equal yes/no, otherwise the maximum deviation
   - ship files changed by the fresh catalog
2. **Scraper:**
   - status, duration and headers of the API and the page
   - status distribution of the model URLs (n of 105)
   - latency p50/max
   - rate-limit headers
3. **Gate:**
   - WPF renders yes/no
   - picture count
   - test duration and total gate job duration
   - hash equality on the same VM, B0↔B without 100i (n of N): **this decides the gate design**
   - hash equality VM↔VM (n of N)
   - duration of the file swap and rebuild in gate-b
   - cross-repo checkout and test in one job yes/no
   - artifact size
4. **Threshold:**
   - method
   - max/p99 of the "same" classes and min/p1 of the "different" class
   - recommended threshold and gap
   - hash equality local↔runner (n of N)
5. **Manifest:**
   - Fields the spike actually needed. Candidates:
     - model SHA as the cache key
     - `gameBuild`
     - catalog SHA
     - the baseline runner's `ImageVersion`
     - holo `formatVersion`
     - `appTag` for the gate
   - Draft fields nobody needed.
   - Alignment with the existing holo manifest (`docs/holo-format.md`).

**"Das ändert sich am Phasenplan"** (what changes in the phase plan) gets its own list. Likely candidates, to be
confirmed or dropped by the numbers:
- **Gate design depends on B0↔B:**
  - If the non-100i pictures are hash-equal, render both states in the same job with a hash-exact comparison. There is
    then no stored baseline and no tolerance mode, and the threshold serves only the judge.
  - Only if they are not equal: a runner-only baseline and a tolerance mode in the picture test (D90 addendum).
- Run the chain without `decimate.ps1`/`run-all.ps1`.
- Move the anchor step from the app repo into this repo.
- **(E1) Cache visibility for T12.2:** workflows from fork PRs can read `actions/cache` (default-branch cache). Either
  keep the catalog out of the cache or disable fork-PR workflows.
- **(E3) File swap before the build, a question for T12.3/T12.5:** add an env override for the data folders to
  `ShipPictureTests` (one line in the app repo), or keep swapping files in the checkout as a pipeline step. The swap works
  but is fragile.

## Verifying the spike itself

- Martin starts the dispatch once with the button. I read the log with `gh run view --log` and fetch the artifacts with
  `gh run download`.
- The spike is done when:
  - all three jobs have run, green or red with an explained finding;
  - `compare.py` has run locally;
  - `TASKS.md` holds all five answers with numbers.
- A second dispatch, for example after a fix, must not call the API again: the log shows the cache hit.
